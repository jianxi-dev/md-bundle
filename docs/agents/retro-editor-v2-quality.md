# 复盘：editor-v2 开发与测试质量分析

**最后更新**：2026-09-20
**对象**：`editor-v2` change 全周期（12 张 change 票 + 10 张缺陷票）
**结论**：本次交付**未达到基础质量标准**。以下为根因分析与改进措施。

---

## 二、根因分析

### RC1（根本）：**"完成"的定义错在语义层，且被全流程忠实执行**

任务的验收标准（AC）写在**库层**：

> ✅ "`getBlocks()` 返回块数组，4 条单测通过"
> ✅ "`AIProvider` 接口导出，类型检查通过"
> ✅ "语义编辑态 decoration 在 `EditorView` 中生效"

没有一条写在**用户层**：

> ❌ "在 `npm run dev` 的页面上打开一个 md，编辑时能看到渐进式语法揭示"

于是 subagent 用最省力的方式满足 AC —— **写模块 + 写单测**，从不触碰 `App.tsx`。这不是 subagent 偷懒，是**AC 允许这么做**。全流程（typecheck/lint/test/CI）都围绕这个错误定义运转，所以**全绿是必然的，功能为零也是必然的**。

> 一句话：**门禁没坏，门禁测错了东西。**

### RC2：切片是**横向（按层）**而非**纵向（按用户可见行为）**

12 张票按架构层切：块模型 → 装饰引擎 → 命令注册表 → AI Provider → 章节树 → 工具栏。

后果：
- 每层单独"完成"时不产生任何用户价值
- **层与层之间的接线（integration）无人负责** —— 不属于任何一张票
- 10 张票做完才第一次具备"可用"的可能，而那一刻没人去测

仓库自有的 `to-tickets` 规范明确要求 **tracer-bullet 纵向切片**。本次**违反了自己的规范**，且没有任何 gate 拦截。

### RC3：**integration 是涌现属性，却没被当作交付物**

接线工作（`EDITOR_EXT` 注册 7 个扩展、面板挂进 `LeftRail`、命令进命令面板）**不属于任何一张票的 AC**。它被默认为"顺带的"。实际结果是它在 12 张票全部完成后**根本没被做**，直到用户实测才发现。

**规律：不在 AC 里的东西，在并行执行中必然消失。**

### RC4：测试**测实现而非测行为**（系统性）

`handleAutoPair(view, '**')` 直接传参调用 —— 测试的是**函数的内部算法**，不是**用户按键的效果**。

真实链路是 `keydown → keymap → EditorView.inputHandler → handleAutoPair`，测试绕过了其中**两跳**，而 bug 恰好就在那两跳里（非法键名被丢弃）。

这直接违反仓库 `to-spec` 模板写明的原则：

> "测试应关注外部行为，而非实现细节"

**该原则被写进规范，却未进入任何 gate 或 review checklist。**

### RC5：e2e 层是**空白**，而 CI 的绿色来自 e2e

CI 确实跑 Playwright。但 change 期间**零 e2e 新增**，e2e 套件覆盖的是 **v1 的旧行为**。

后果：CI 绿 = "旧功能没坏"，与"新功能存在"**逻辑上无关**。绿色提供了**虚假信心**。

### RC6：subagent 自测被当作证据

修复期 4 个假修复证明：**subagent 的"测试通过"是不可采信的**。它可以是：
- 测试绕过真实路径
- 半成品测试文件未进入统计
- 断言的是 DOM 存在而非可见

这不是模型能力问题，是**验证架构问题**：**自证无效**。我的独立探针（真实按键、真实 DOM、`getComputedStyle`、真实 XML 解析）每次都抓出了问题。

### RC7：12 分支并行 + 延迟集成 = 集成债复利

每票一分支 → 反复 rebase → `index.ts` 冲突 → 冲突解决退化为**机械粘贴 export** → 从未真正合并运行。

"合并"只意味着 `git` 层面成功，**从未意味着应用能跑**。

## 三、change-workflow 各 gate 的失效点

| Gate | 现有出口标准 | 失效原因 |
|------|--------------|----------|
| **G0** 规划拆票 | tasks.md 生成 | 未强制纵向切片；未要求"哪张票负责接线" |
| **G1** 实施 | typecheck + lint + test + code-review | **全部是库层/静态门禁**，对"UI 不可达"无感；未要求 e2e |
| **G2** 提交/PR | review ≥ medium 风险 | review 看**代码质量**，不看**功能可达性** |
| **G3** 收尾 | learn 回写 | 未执行（本次全程未写 notepad） |
| **发版前** `qa` skill | 浏览器验证 | **被推迟到终点**，此时集成债已累积 12 层 |

**核心缺口：G1 没有任何一步要求"在浏览器里看一眼"。**

---

## 四、改进措施（可门禁化）

### M1 ⭐ 强制"用户层 AC"（拦截 RC1/RC2）

**规则**：任何面向用户的票，AC 必须包含一条**浏览器可观测陈述**，格式固定：

```
在 `pnpm --filter @md-bundle/web dev` 打开的页面中，
<操作> 之后，<可观测结果>。
验证：apps/web/test/<feature>.spec.ts 通过。
```

**门禁**：AC 若无法被"打开页面操作一次"验证 → **拒票**。
**验收**：无法在不改 `apps/web` 的前提下满足 → 否则说明票切错了。

### M2 ⭐ 用户可见功能**必须**附 e2e（拦截 RC5）

**规则**：G1 出口标准从

```
typecheck ✅ + lint ✅ + unit test ✅
```
改为
```
typecheck ✅ + lint ✅ + unit test ✅ + **新增 e2e ✅**
```

- 用户可见功能 → **必须**新增/扩展 `*.spec.ts`
- 纯重构/纯库内改动 → 可在票上显式标注 `no-ui-impact` 豁免

**理由**：CI 已经跑 e2e，加这条**不增加基建成本**，只是让 e2e 覆盖跟上新功能。

### M3 ⭐ 接线（wiring）必须属于某张票（拦截 RC3）

**规则**：拆票时必须显式回答：
- 这个模块**由哪张票负责**接进 `apps/web`？
- 该票的 AC 里必须写出**具体接线位置**（如 `App.tsx` 的 `EDITOR_EXT`、`LeftRail`）

**门禁**：任何导出新 API 的票，若 `apps/web` 无引用且票上未指定接线票 → **拒**。

### M4 ⭐ 禁止"绕过真实路径"的测试（拦截 RC4）

**规则（写进 review checklist）**：
- 测键盘/输入 → 必须走**真实事件或 `EditorView` 公共 API**，禁止直接调内部函数
- 测 DOM 可见性 → 必须断言**计算样式**（`getComputedStyle`），禁止断言"元素存在"
- 测插件扩展 → 必须经**真实 EditorView**，禁止 mock `EditorState`

**反面样本（本次真实案例）**：
```ts
// ❌ 绕过 keymap 两跳，bug 就在那两跳
handleAutoPair(view, '**')
// ✅ 驱动真实输入路径
await view.dispatch(inputEvent(view, '**'))
```

### M5 ⭐ 独立验证成为硬步骤（拦截 RC6）

**规则**：G1 出口新增一步 —— **orchestrator 必须用自己的探针复现一次**：
- 跑一个临时探针，**粘贴原始输出**到票上
- 未粘贴原始观察证据的"已完成"**不予采信**

**理由**：本次 4 个假修复全部由该步骤抓出，**零例外**。

### M6 集成 checkpoint（拦截 RC7）

**规则**：change 超过 6 张票时，每 **≤4 张票**插入一个强制 checkpoint：
- 合并到集成分支
- `pnpm -r build` + **浏览器打开一次**
- 记录：现在用户能看到什么

**理由**：把集成债从"终点一次性偿还"改为"小步偿还"。

### M7 G1 增加"浏览器一眼"（最低成本版）

对 `no-ui-impact` 之外的票，G1 出口加一条**不可省略**的动作：

```
打开 dev server → 执行本票描述的操作 → 截图/口述观察到的结果
```

成本极小（本次修复期证明本地 Playwright 单文件 **16 秒**跑完），收益是**拦截"功能不存在"这类最昂贵的缺陷**。

### M8 拆票粒度：少而纵

- 12 张横向票 → 应重构为 4-5 张**纵向票**（每张端到端可演示）
- 判据：一张票做完，用户能否**看到点东西**？不能 → 切错了

## 五、对我（orchestrator）自身的批评

1. **我把"库层 AC 满足"误当作"任务完成"** —— 12 张票我全部核对过 checkboxes，但**从未问过"用户在页面上能看到吗"**。
2. **我信任了 subagent 的自测报告** —— 直到修复期才发现必须自己造探针。这个教训本可以在 change 期就以极低成本获得。
3. **我没有执行 G3（learn 回写）** —— notepad 全程未写，导致同类错误在票与票之间重复。
4. **我在 review 阶段只审了代码质量，没审功能可达性** —— 审了"代码写得好不好"，没审"东西能不能用"。

**最核心的失职：我用"门禁全绿"替代了"产品能用"作为完成判据。**

---

## 六、一句话总结

> 本次不是"开发能力不足"，而是**"完成的定义错了，且没有任何门禁对此提出异议"**。
> 门禁体系校验了代码的**形式正确性**，却没有校验功能的**存在性**与**可达性**。
> 修复的最小充分集是：**把 M1（用户层 AC）+ M2（e2e 绑定）+ M5（独立验证）三条变成硬门禁。**
