# Markdown 编辑器 v3 — AI 时代的文档交互范式

> **这不是一个更好的编辑器。这是一种新的文档交互方式。**
>
> **核心洞察**：AI 时代，Markdown 不再是"写给人看的标记语言"，而是**人与 AI 共享的结构化意图载体**。编辑器不再是"打字工具"，而是"人机协作的画布"。

---

## 0. 从豆包看基准线（我们看到的现实）

从截图分析，豆包的 MD 编辑器提供的能力：

| 能力 | 豆包 | 问题 |
|------|------|------|
| 块手柄（T + 拖拽） | ✅ | 仅格式转换 + 基础操作 |
| 斜杠菜单 | ✅ | AI 帮我写 + 基础格式 + 小组件 |
| 插入菜单 | ✅ | 正文/标题/列表/代码/引用/表格/分栏/高亮块/公式 |
| AI 入口 | ✅ 问问豆包 + AI 帮我写 | **只是两个按钮，没有深度集成** |
| 表格 | ✅ 网格选择器 7x3 | 插入后编辑能力未展示 |
| 分栏 | ✅ 栏位可视化选择器 | 仅布局，无内容感知 |
| 文本绘图 | ✅ 文档小组件 | 入口级，无后续交互 |
| 颜色/评论/翻译 | ✅ 块级操作 | 翻译是块级，非实时协作 |

**豆包的本质**：在传统 Markdown 编辑器上**贴了 AI 入口**，但编辑体验和 AI 能力是**两个世界**。用户需要在"编辑模式"和"AI 对话"之间来回切换。

**所有大厂的共同问题**：
1. AI 是"外挂"——一个聊天按钮，不是编辑器的内在能力
2. 文档是"静态的"——AI 读完就忘，没有持久化的文档理解
3. 交互是"命令式的"——用户输入 → AI 输出 → 手动粘贴
4. 没有"意图流"——AI 不知道用户下一步想做什么
5. 文档结构是"扁平的"——标题/列表/段落对 AI 来说只是文本，不是语义

## 1. AI 时代 Markdown 缺失的关键能力

### 1.1 从"打字"到"意图表达"

**现状**：用户必须精确输入 Markdown 语法来表达意图。
**缺失**：编辑器应该理解用户的**意图**，而非**操作**。

```
传统流程：
  用户想"把这段文字变成重要提示"
  → 用户记住 callout 语法
  → 用户输入 > [!NOTE]
  → 用户把文字粘贴进去

AI 时代流程：
  用户选中文字
  → 用户说"这很重要"
  → 编辑器自动转为 callout（类型、颜色、图标）
```

### 1.2 从"静态文档"到"活的文档"

**现状**：文档是死的文本文件，每次打开都要重新理解。
**缺失**：文档应该携带**结构化的语义记忆**，让 AI 和人都能快速理解。

### 1.3 从"人写 AI 看"到"人机共写"

**现状**：人写完，AI 读。AI 建议，人粘贴。
**缺失**：人和 AI 在同一文档上**同时工作**，AI 理解上下文，人掌控方向。

### 1.4 从"格式化"到"意义化"

**现状**：Markdown 的 `#` 只是"大号字体"。
**缺失**：`#` 是文档的**骨架**，AI 应该能理解"这是一个论点，下面三个是论据"。

## 2. 核心创新：「意图引擎」(Intent Engine)

### 2.1 什么是意图引擎

不是命令面板，不是 AI 聊天框，而是一个**理解用户当前状态并主动提供帮助**的系统。

```
┌─────────────────────────────────────────────────────────┐
│  Intent Engine                                          │
│                                                         │
│  输入层：                                               │
│  ├─ 用户正在做什么（选中/输入/拖拽/停顿）               │
│  ├─ 光标在哪里（标题中/列表中/表格中/空行）             │
│  ├─ 文档结构是什么（大纲/块类型/层级关系）              │
│  └─ 用户历史模式（最近操作/常用命令/偏好）              │
│                                                         │
│  推理层：                                               │
│  ├─ 用户可能想做什么（概率排序）                        │
│  ├─ 当前块可以做什么（可用操作）                        │
│  └─ 文档整体需要什么（结构完整性检查）                  │
│                                                         │
│  输出层：                                               │
│  ├─ 主动建议（轻量提示，不打断）                        │
│  ├─ 快捷操作（一键执行）                                │
│  └─ AI 协作请求（用户确认后执行）                       │
└─────────────────────────────────────────────────────────┘
```

### 2.2 意图驱动的交互示例

**场景 1：用户输入了一段列表**
```
用户输入：
- 第一点
- 第二点
- 第三点

编辑器检测到：用户创建了 3 项列表
主动建议（列表下方淡灰色小字）：
  "💡 转为看板 · 转为表格 · 添加摘要"
用户点击"转为看板" → 自动转为 Kanban 块
```

**场景 2：用户选中了一段文字并停顿 2 秒**
```
编辑器检测到：用户选中了 120 字文本，停顿
推断：用户可能在思考如何处理这段文字
主动建议（选中下方浮动条）：
  "✂️ 缩短 · 📝 改写 · 🌐 翻译 · 📊 提取要点 · 🔍 解释"
用户点击"提取要点" → AI 生成要点列表替换原文
```

**场景 3：用户写了一个标题但下面没有内容**
```
编辑器检测到：H2 标题后跟空行
推断：用户准备写这一节但可能没有思路
主动建议（空行处淡灰色）：
  "✨ AI 帮我写这一节 · 📋 从模板插入 · 📎 粘贴内容"
```

**场景 4：用户写了一篇长文但没有目录**
```
编辑器检测到：文档 > 500 字，有 3+ 个标题，无 [TOC]
推断：用户可能需要导航辅助
主动建议（标题区右侧小按钮）：
  "📑 插入目录"
```

### 2.3 意图引擎 vs 传统自动完成

| 维度 | 传统自动完成 | 意图引擎 |
|------|-------------|----------|
| 触发时机 | 用户输入特定字符（`/`、`#`） | 用户行为模式（停顿、选中、重复） |
| 理解深度 | 当前字符 | 当前块 + 文档结构 + 用户历史 |
| 交互模式 | 被动等待用户命令 | 主动建议 + 一键确认 |
| AI 角色 | 无 | 核心推理层 |
| 学习能力 | 无 | 越用越懂用户 |

## 3. 核心创新：「语义画布」(Semantic Canvas)

### 3.1 什么是语义画布

不是无限画布（Miro 式），而是**文档结构的可视化交互层**。

文档不只是从上到下的文字流——它是一棵树、一张图、一个可以**从不同角度观察和操作**的结构。

```
传统视图（线性）：
  # 标题
  段落1
  ## 子标题
  段落2
  列表...
  ### 子子标题
  段落3

语义画布视图（结构）：
  ┌─────────────────────────────────────────┐
  │ 📄 文档标题                              │
  │ ├── 📝 段落1（论点）                     │
  │ ├── 📂 子标题（论据组）                  │
  │ │   ├── 📝 段落2（论据A）               │
  │ │   └── 📊 列表（支持数据）              │
  │ └── 📂 子子标题（结论）                  │
  │     └── 📝 段落3                         │
  └─────────────────────────────────────────┘
  拖拽重组 · 折叠展开 · 颜色标记 · AI 分析
```

### 3.2 画布操作

| 操作 | 效果 |
|------|------|
| 拖拽子树 | 移动整个章节（含所有子块） |
| 折叠/展开 | 隐藏/显示子结构 |
| 颜色标记 | 标记章节状态（草稿/完成/待审） |
| AI 分析 | 选章节 → "检查逻辑连贯性" |
| 大纲跳转 | 点击节点 → 编辑态跳转到对应位置 |
| 导出子树 | 选中章节 → 导出为独立文档 |

### 3.3 画布与编辑态的关系

```
┌──────────────────────────────────────────────┐
│ 顶部工具栏：[编辑] [画布] [预览] [AI 协作]    │
├──────────────────────────────────────────────┤
│                                              │
│  编辑态（默认）：语义编辑态，所见即所得       │
│  ─────────────────────────────────────────── │
│  画布态：文档结构可视化，拖拽重组             │
│  ─────────────────────────────────────────── │
│  AI 协作态：人机共写，AI 实时辅助             │
│                                              │
└──────────────────────────────────────────────┘
```

## 4. 核心创新：「AI 协作态」(AI Collaboration Mode)

### 4.1 不是聊天框，是共写空间

**所有现有产品的 AI 集成**：一个侧边栏聊天框，用户复制粘贴。
**我们的 AI 协作态**：AI 直接在文档上工作，用户实时看到 AI 的修改。

### 4.2 AI 协作的三种模式

#### 模式 A：AI 助手（被动响应）
```
用户选中文本 → 右键 → "AI" → 选择操作
AI 在原地修改，用户可撤销

操作类型：
  ✂️ 缩短：保留核心信息
  📝 改写：改变语气/风格
  🌐 翻译：翻译为目标语言
  📊 结构化：转为列表/表格/看板
  🔍 解释：添加注释说明
  ✅ 事实核查：标记可能有误的陈述
```

#### 模式 B：AI 共写（主动协作）
```
用户开始写一篇文章
AI 实时理解文档结构和意图

当用户写到一半停顿时：
  AI 建议："根据前面的结构，下一节可能需要：
   1. 对比分析
   2. 案例说明
   3. 数据支持
   需要我帮你起草其中一节吗？"

用户选择 → AI 在对应位置生成草稿 → 用户编辑完善
```

#### 模式 C：AI 代理（自主执行）
```
用户给出高层指令：
"把这篇技术文档改写成面向非技术读者的版本，
 保留所有技术细节但用类比解释，
 每节末尾加一个'关键要点'总结。"

AI 执行：
  1. 读取全文，理解结构
  2. 逐节改写（流式显示进度）
  3. 每完成一节，标记为"待审核"
  4. 用户逐节确认/修改
  5. 全部完成后，生成变更摘要
```

### 4.3 AI 的文档记忆

**关键创新**：AI 不是每次都从零开始理解文档。

```
文档首次打开 → AI 生成"文档指纹"：
  ├─ 结构大纲（标题层级、块类型分布）
  ├─ 主题提取（关键词、核心概念）
  ├─ 写作风格（句式、用词、语气）
  ├─ 逻辑流（论点-论据关系）
  └─ 待办标记（用户标注的 TODO/待完善）

后续交互 → AI 基于指纹快速理解上下文：
  "用户在第 3 节第 2 段停留了 5 分钟，
   这段讨论的是 X 概念，与第 1 节的 Y 形成对比，
   用户可能想添加一个类比说明。"
```

## 5. 核心创新：「文档即程序」(Document as Program)

### 5.1 概念

参考 MarkdownAI、MAGI、Knowgrph 的前沿思路，但**不引入私有语法**。

核心思想：Markdown 文档不仅是内容，还可以携带**可执行的意图**。

### 5.2 实现方式：结构化注释

```markdown
# 季度报告

<!-- ai:purpose 本文档用于向管理层汇报 Q3 产品进展 -->
<!-- ai:audience 非技术管理层，关注业务指标 -->
<!-- ai:tone 专业、简洁、数据驱动 -->

## 核心指标

<!-- ai:check 确保以下数据与财务系统一致 -->
<!-- ai:source https://internal-dashboard.example.com/q3 -->
| 指标 | Q2 | Q3 | 变化 |
|------|-----|-----|------|
| DAU | 10K | 15K | +50% |

## 产品进展

<!-- ai:todo 需要补充用户反馈数据 -->
<!-- ai:suggest 考虑添加竞品对比分析 -->

我们的产品在 Q3 实现了...
```

**这些注释**：
- 人看不到（渲染时自动隐藏）
- AI 能读取（作为上下文指令）
- 编辑器能解析（在对应位置显示 AI 建议）
- 导出时自动去除（保持 Markdown 纯净）

### 5.3 动态内容块

文档中可以嵌入**动态计算的内容**：

```markdown
## 实时数据

<!-- ai:query select count(*) from users where created_at > '2026-07-01' -->
<!-- ai:format 数字，带千分位 -->
本季度新增用户：**{{result}}** 人
```

- 纯文本状态下：显示为 `本季度新增用户：**加载中...**` 或上次缓存值
- 连接数据源后：自动更新
- 导出为 HTML/PDF 时：渲染为最终值
- 不连接数据源时：优雅降级为占位符

### 5.4 为什么不是私有语法

| 方案 | 优点 | 缺点 |
|------|------|------|
| MAGI 私有语法（`.mda`） | 表达力强 | 破坏 Markdown 可移植性 |
| 纯注释（我们的方案） | 100% 兼容标准 Markdown | 表达能力受限 |
| frontmatter 指令 | 结构化 | 只能文档级，不能块级 |

**选择注释方案**：因为我们的护城河是"编辑体验"，不是"文档格式"。Markdown 的可移植性是底线。

## 6. 核心创新：「流式编辑」(Fluid Editing)

### 6.1 概念

现有编辑器的交互是**离散的**：输入 → 渲染 → 再输入 → 再渲染。
流式编辑是**连续的**：编辑和渲染之间没有明确边界。

### 6.2 具体实现

#### 打字即渲染
```
用户输入 **重要**
→ 不等待用户输入闭合的 **
→ 立即渲染"**重要**"中的"重要"为粗体
→ 用户继续输入时，粗体范围自动扩展
→ 用户输入 ** 闭合 → 粗体结束
```

#### 选择即操作
```
用户选中一段文字
→ 立即出现浮动工具栏（不需要右键或快捷键）
→ 工具栏内容根据选中内容类型动态变化
→ 选中文本是 URL → 显示"打开链接 / 编辑链接 / 转为引用"
→ 选中文本是代码 → 显示"复制 / 运行 / 解释"
→ 选中文本是数字 → 显示"转为图表 / 添加单位 / 计算"
```

#### 拖放即重组
```
用户拖拽一个列表项
→ 实时显示放置位置（蓝色指示线）
→ 放置后自动重新编号
→ 如果拖到另一个列表 → 合并
→ 如果拖到列表外 → 转为段落
```

#### AI 辅助即编辑
```
用户在写一段技术描述
→ AI 实时理解上下文
→ 在行间显示淡灰色建议文本（类似 GitHub Copilot 的 ghost text）
→ Tab 接受建议，继续输入忽略
→ AI 建议不是"替你写"，而是"帮你接着写"
```

### 6.3 流式 vs 传统

| 维度 | 传统编辑 | 流式编辑 |
|------|----------|----------|
| 输入-渲染 | 离散（输入完再渲染） | 连续（输入同时渲染） |
| 操作触发 | 显式命令（快捷键/菜单） | 隐式意图（选择/停顿/模式） |
| AI 角色 | 外挂（需要手动调用） | 内在（始终在线，按需激活） |
| 文档状态 | 静态（保存后才稳定） | 动态（始终响应变化） |
| 用户心智 | "我在用编辑器" | "我在写文档" |

| 模式 | 适合场景 | 核心交互 |

## 9. 实施路线图

### Phase 0: 基础设施（2 周）
- 块模型定义 + Lezer AST 迁移
- 统一命令注册表

## 10. 设计哲学

> **"编辑器不是工具，是伙伴。"**

1. **意图优先**：用户不需要记住语法，编辑器理解意图
2. **AI 内在**：AI 不是外挂，是编辑器的神经系统
3. **流式连续**：编辑和渲染之间没有边界
4. **文档即意图**：Markdown 不只是格式，是人与 AI 的共享思维
5. **开放一切**：纯前端、零锁定、标准 Markdown 输出
