产品开发最佳实践总结

1

决策驱动开发

所有重大决策写入 decisions.md，每条决策包含 Considered Options（被否选项及理由），避免「当时为什么这样选」的失忆。

触发技能：/grill-me, /batch-grill-me —— 通过对抗式问答暴露隐藏假设
2

计划审查员机制

复杂计划（v2 共 29 任务）必须经过 Momus 多轮对抗评审。7 次 REJECT→修复→APPROVE 的循环，比「一次性通过」更能发现隐藏风险。

触发技能：Momus 评审 —— 独立审查员找出逻辑漏洞和范围蔓延
3

分层计划结构

decisions.md（决策）→ .omo/plans/*.md（可执行计划）→ openspec/changes/（产品规格）。三层分离确保「为什么做」与「做什么」不混在一起。

关键产出：6 Waves 分组 + F1-F4 终审，每 wave 结束全绿才推进
4

知识自动沉淀

.omo/notepads/learnings.md 自动积累技术细节（如 CM6 undo 在 macOS 需 Meta+z）。679 行笔记成为后续任务的上下文。

关键价值：子代理每次任务前读取 notepads，避免重复踩坑
5

Atlas 编排模式

Orchestrator 永不写代码，只负责分解任务 → 并行委派 → 验证 → 更新 checkbox。6 个独立任务并行执行，总耗时 4 分钟。

关键原则：PARALLEL by default，SEQUENTIAL only with named dependency
6

缺陷与规格衔接

GitHub Issues 与 OpenSpec 变更记录打通：新 bug → Issue；新需求 → OpenSpec change；修复 Issue 时同步更新 tasks.md。

关键产出：docs/agents/ 文档让 Agent 知道如何消费领域知识

用户实践经验补充

OpenSpec 工作流：/opsx-propose → spec → /implement

使用 /opsx-propose 创建 change 并生成 spec，然后可用 /implement 替代 /tdd 进行开发执行。

需求变更/丰富/优化：使用 /opsx-update-change 修订现有 plan，或 /openspec-explore 澄清需求。

简化验证流程：implement → 人工测试 → 提交

执行 /implement 或 /tdd 后，不需要再单独调用 review/QA 技能。人工测试通过后，直接执行后续推荐技能并提交即可。

技能组合：/implement → （人工测试）→ /document-release → commit

知识沉淀双通道：自动 notepads + /learn → sync-gbrain

子代理会自动写入 .omo/notepads/。此外，提交代码后可显式调用 /learn 捕获学习，然后运行 /sync-gbrain 进行解析量化。

工作流：commit → /learn → /sync-gbrain → 知识进入 gbrain 长期存储

关键操作建议

关于「活的源码」编辑范式

v2 的核心创新是「Typora 式装饰编辑」，但底层永远是 Markdown 源码。这是块编辑器（Milkdown/TipTap）与源码编辑器的中间路线——观感所见即所得，数据契约仍是「源文件即真相」。建议在产品文档中强调此点，避免用户困惑。

关于共享渲染器的双向输血

@md-bundle/renderer 从 clairis 抽取，供 web 端使用；未来 web 端的编辑能力（装饰/页签）也将反哺 clairis。建议在两仓库之间建立版本同步机制（如 changeset），避免 API 漂移。

关于 FSA 渐进增强

文件系统访问 API 仅 Chromium 支持，v2 设计已考虑降级路线（无 FSA 时主按钮显示「下载」、文件树隐藏）。建议在 QA 中重点测试无 FSA 场景，确保 v1 等价体验全程可用。

关于分享对象 = 网站

v2 推翻 v1 的「文档分享」语义，改为「网站邀请」。邀请链接仅含 `?ref=invite&by=<昵称>`，无文档 payload，服务端零存储。这是正确的产品定位（工具 vs 内容平台），但需在用户引导中明确区分「邀请朋友用工具」vs「分享我的作品」。

关于随机昵称的可测试性

邀请链接的随机昵称通过 `randomNickname(rng?)` 生成，支持注入 RNG 种子以便测试。建议保留此注入缝，并在测试文档中说明如何固定种子生成确定性昵称。
