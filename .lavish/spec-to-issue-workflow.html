3.7 · 双轨并行:主窗口开发 + worktree 修 Bug(新增)

双窗口分工(你已在用,机制可完全复用)

主窗口(feat/docx-export-quality)
功能 agent 捡 feat 类 ticket → 开发 → PR → 分级合并。长生命周期。
worktree(md-bundle-fix 挂 fix)
缺陷 agent 捡 ready-for-agent bug issue → fix/<slug> → 原子修复 → PR → 分级合并。短生命周期。
互不阻塞
两窗口各自独立建 PR,CI 各自跑,合并各自回 main。同一套 triage + PR 自动化机制直接复用,只是分支前缀(feat vs fix)与起点不同。

关键规则(避免冲突)

fix 分支基于 origin/main,不基于 feat——修复可独立合入,不依赖功能线。
重叠区域冲突:若 fix 与 feat 改同一文件,先合 fix 到 main,feat 再 rebase main 消化,不反向。
worktree 基线干净:worktree 只检出 git 跟踪文件,无 .omo 噪音——天然适合原子 bug 修复,reset --hard 也不伤主窗口规划。
频繁同步:feat 定期 merge main 保持落后可控;fix 完成即合入 main,不留堆积。
worktree 环境注意:worktree 里 openspec/.omo 等运行时需重建或直读主窗口路径(less /Users/mason/ToHighs/md-bundle/.omo/plans/xxx.md)——你的 branch-workflow.md 6.3 已记录。
落地形态:两个窗口各跑一套 pr-automation.sh(参数区分 --role feat|fix)。主窗口 agent 处理功能 ticket,worktree agent 处理 bug ticket,双方都从 gh issue list --label ready-for-agent 拉活、按各自前缀建分支。这就是你的 branch-workflow.md 6.1 分工原则 + 本方案自动化的合并。
执行调度模型(回答:并行还是串行?)
默认双线并行,冲突时自动降级串行。 功能 issue 与 bug issue 同时存在时:
  • 并行(默认):主窗口 agent 跑 feat 线(功能 issue → feat/<slug> → PR),worktree agent 跑 fix 线(bug issue → fix/<slug> → PR)。两线独立建分支、独立 CI、独立合并回 main。前提:两线改动文件不重叠(agent 开工前先 git diff origin/main --name-only 预判冲突面)。
  • 串行降级(重叠时):若两线触及同一文件/模块,自动串行——先合 fix 到 main(bug 小、快、稳),feat 再 rebase main 消化,不反向。此时 worktree fix 线先行,主窗口 feat 线等待 rebase。
  • 多 agent 会话:两条线可由两个独立 agent 会话各领一条(一个在主窗口、一个在 worktree),互不阻塞;也可单 agent 会话按"fix 优先"顺序处理。
  • 优先级规则:P0/P1 bug 永远插队先走(合入 main 后 feat rebase);P2/P3 bug 可等 feat 空闲窗口。
一句话:不是"一个分支串行做完所有事",而是"两条分支并行推进,冲突时 fix 优先、feat 跟随"。

3.10 · Change 级收尾自动触发(新增,已落地)

你问的 opsx 命令:sync / archive / update 在自动化流程中是否还有必要?结论:必要,且已设计为自动触发——agent 检测到 change 全部 tasks 完成 + PR 全合并,自动执行 update(如有漂移)→ sync → validate → archive,无需手动喊命令。propose 保留为起点,apply 被 implement 替代,continue 基本退出(propose 已一次生成全部 artifacts)。

opsx 命令在机制中的定位

propose — change 起点,保留(现已在用)
apply — 实施通道,与 implement 二选一(机制已定 implement)
update — 实施中漂移修订,change 级收尾第 1 步(无漂移跳过)
sync — delta 合并回主 spec,change 级收尾第 2 步
archive — change 归档,change 级收尾第 4 步
continue — 补全缺失 artifacts,基本退出(propose 已一次生成全部)

agent brief 质量:triage 转 ready-for-agent 必须附 agent brief(行为契约,不写文件路径),否则执行 agent 会乱猜。

Q5 · 自动合并执行方式?
推荐:GitHub 原生 auto-merge + 分支保护。 main 设 required status checks(ci.yml 两个 job),PR 创建时 agent 按风险等级决定:risk-low → gh pr merge --auto --squash 启用 auto-merge(CI 绿自动合);中/高不启用,等人工。零新增 workflow 文件,原生可靠,配合 deleteBranchOnMerge 自动收尾。
Q6 · risk-medium 单人提速?
推荐:降级为"合后即时验证",核心模块例外。 单人维护没有第二个人评审,等待=等自己。默认 medium 也自动合,但 merge 后立即跑线上检查(curl 首页 + CI deploy 绿 + console 无错);标 risk-high 或涉及渲染/保存/FSA 的强制人工审 diff。实际等效两级:low+medium 自动、high 人工。
Q8 · PR 自动化落地形态?
推荐:先脚本 + 文档,验证稳定后再 skill 化。 写 scripts/pr-automation.sh(确定性命令序列:建分支→自检→commit→push→pr create→分级 auto-merge)并把流程规范写进 docs/agents/ 或你的 branch-workflow.md。跑通 3-5 个真实 PR 后,把经验包装成 skill。脚本不依赖 LLM 判断,可测可回滚。
Q7 · worktree 还是主窗口? 保持你的结论:顺序推进用主工作区分支切换,真并行才 worktree。md-bundle 现状维持。
